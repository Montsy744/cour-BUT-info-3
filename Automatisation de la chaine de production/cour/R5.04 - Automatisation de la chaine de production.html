Gitlab

Le fichier .gitlab-ci.yml permet de décrire l’ensemble des étapes de l’intégration et du déploiement continu de la branche courante du code.

Il est écrit en YAML.

La documentation de référence : https://docs.gitlab.com/ee/ci/yaml/

Il est composé de job regroupés en stage

Job

nom-du-job:
  image: debian:sid
  script:
    - apt-get update && apt-get install -y make
    - make test
  • nom-du-job : le nom du job
  • image : l’image docker à utiliser pour lancer ce job
  • script : le script shell qui sera lancé dans le container image

Étapes

stages:
  - 🧪 tests
  - ⭐ deploy

unit-test:
  stage: 🧪 tests
  ...

Ce pipeline est composé de 2 étapes (stage) successives : 🧪 tests et ⭐ deploy l’étape ⭐ deploy ne se lancera que si l’étape 🧪 tests c’est bien terminée.

Fonctionnement interne de gitlab-ci

Fonctionnement interne de gitlab-ci

Les 3 acteurs

  • Gitlab : le coordinateur, il stocke le dépôt, parse le .gitlab-ci.yml et déclenche les jobs
  • Le runner : le worker qui exécute les jobs, il peut être n’importe où
  • Le container : l’environnement d’exécution du job, défini par la directive image:

Le coordinateur

  • À chaque push, gitlab lit le .gitlab-ci.yml de la branche poussée
  • Il crée un job pour chaque job éligible de chaque stage
  • Les jobs attendent qu’un runner libre les prenne (pick)
  • Gitlab ne fait qu’ordonnancer, jamais exécuter.

Le runner

  • Un programme (gitlab-runner) installé sur une machine, déclarée auprès de gitlab
  • Il demande en boucle au coordinateur : « as-tu un job pour moi ? »
  • Quand un job lui est attribué :
    • il lance un container depuis l’image image:
    • il exécute le script dedans
    • il remonte le flux de sortie et le code de sortie au coordinateur
  • Il supprime le container, rien ne survit, sauf les artifacts

Le runner

Un runner peut exécuter plusieurs jobs en parallèle et plusieurs runners peuvent se partager un même projet.

  • les jobs d’un même stage peuvent partir sur des runners différents : ils doivent être indépendants

Conséquences pratiques

  • Job bloqué en pending : pas de runner disponible (ou aucun tag ne correspond)
  • Jobs d’un même stage : parallèles et indépendants, pas de variable partagée, pas d’état d’un job à l’autre
  • Le container est jetable : tout ce qui n’est pas commité ou archivé en artifact est perdu
  • Le runner est « près » du code : sur l’infra de l’IUT ou sur celle de gitlab.com

Les runners que nous utilisons

  • Runners partagés de gitlab.com : fournis par gitlab, déjà enregistrés, c’est ce que nous utilisons dans les TP
  • Runner dédié : enregistré par l’équipe pour son projet (autoscaling, machine plus puissante, réseau privé, etc.)

C’est pourquoi les TP utilisent gitlab.com et pas l’instance universitaire : les runners partagés n’y sont pas activés.

Enregistrer un runner

# sur la machine qui sera le runner
gitlab-runner register
# donner l'url du coordinateur et le token du projet

Le runner apparaît ensuite dans Settings > CI/CD > Runners.

Dans ce cours, vous n’aurez pas à enregistrer de runner : les runners partagés de gitlab.com suffisent.

La directive services

job:
  image: debian
  services:
    - name: docker:dind
      alias: docker
  script:
    - docker version
  • image: : le container du job
  • services: : des containers voisins, démarrés en plus du job
  • Le job les atteint par le réseau via leur alias (résolution DNS)

services : docker:dind

  • dind = Docker in Docker : un daemon docker complet dans un container voisin
  • Le job (par ex. docker:latest, qui n’a que le client) lui envoie ses commandes
  • C’est ce qui permet de docker build dans un job gitlab-ci

Devops or not devops

  • Devops est un mouvement visant à l’alignement de l’ensemble de l’entreprise sur un objectif commun
  • Devops n’est pas une méthode
  • Devops n’est pas un rôle
  • Devops n’est pas un titre

Et pourtant

Il n’y a pas de définition dans le dictionnaire.

devops

Devops est la concaténation des trois premières lettres du mot anglais development (développement) et de l’abréviation usuelle ops du mot anglais operations (exploitation). Le mot a été inventé par Patrick Debois en 2009.
