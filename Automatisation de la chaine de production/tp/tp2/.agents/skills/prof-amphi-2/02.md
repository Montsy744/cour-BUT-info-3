# La norme Unix

Tout programme exécuté en ligne de commande suit le même contrat :

* **stdin** : l'entrée standard, ce que le programme lit
* **stdout** : la sortie standard, le résultat du programme
* **exit code** : le code retour du programme
    * `0` : tout s'est bien passé
    * autre valeur : une erreur s'est produite

Visible dans le shell avec `$?` :

```shell
$ make test
All tests passed
$ echo $?
0

$ make test
Error: expected 42, got 43
$ echo $?
2
```

# Gitlab-ci exploite cette norme

Le `script` d'un job est exécuté ligne par ligne par le runner :

* **Exit code** : à la première commande qui retourne autre chose que `0`, le job s'arrête et passe au rouge
* **Stdout / stderr** : tout ce qui s'affiche est remonté au coordinateur, c'est le **log du job** dans l'interface gitlab

Un job gitlab-ci n'est pas magique : c'est un programme qui respecte la norme Unix.

# Un job ne commit pas

**Règle : un job ne modifie jamais le dépôt** (ni `git commit`, ni `git push`)

* Un job détient des secrets et des identifiants : une fois compromis, il peut écrire dans le code de tout le monde
* Un commit fait depuis le job redéclenche le pipeline : boucle infinie
* C'est voulu : le `CI_JOB_TOKEN` ne permet pas de pusher sur le dépôt

# Formater sans commiter

Le job de formatage est **non destructif** : il vérifie, il ne modifie jamais le code.

```yaml
fmt:
  stage: 🔎 quality
  image: maven:3-eclipse-temurin-21
  script:
    - mvn fmt:check
```

* Code mal formaté : exit code différent de `0`, le job passe au rouge
* C'est au développeur de formater et de commiter

# Maven

Dépendances et séquence de construction

* Cycle de vie complet : `validate` → `compile` → `test` → `package` → `verify` → `install` → `deploy`
* Une commande exécute **toutes** les phases jusqu'à celle demandée

Les phases utilisées dans le cours :

* `compile` : compiler le code source
* `test` : lancer les tests unitaires
* `package` : construire le livrable (jar)
* `verify` : contrôler la qualité (tests d'intégration, couverture)

# Rappel : la plomberie gitlab-ci

Vu en amphi 1, et touché du doigt en TP1 :

* Le **coordinateur** (gitlab) ordonnance, il n'exécute rien
* Un **runner** libre prend le job et lance un **container** jetable depuis l'image `image:`
* Rien ne survit au job, sauf les **artifacts**
* En TP1 : job *pending* (pas de runner libre), container perdu en fin de job, `docker:dind` en container voisin

# Artefacts

```yaml
junit:
  stage: 🧪 tests
  image: maven:3-eclipse-temurin-21
  script:
    - mvn verify
  artifacts:
    reports:
      junit: "target/surefire-reports/*.xml"
      coverage_report:
        coverage_format: jacoco
        path: target/site/jacoco/jacoco.xml
```

Le rapport de couverture alimente le diff enrichi des merge requests et la vue couverture de gitlab.

# Docker:dind

Vu en TP1 : un daemon docker complet en container voisin du job, pour builder et pousser l'image.

```yaml
docker-build:
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker login -u gitlab-ci-token -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $CONTAINER_NAME .
    - docker push $CONTAINER_NAME
```

# Badges : extraire la couverture

```yaml
junit:
  stage: 🧪 tests
  image: maven:3-eclipse-temurin-21
  coverage: '/Total.*?([0-9]{1,3})%/'
  script:
    - mvn verify
    - cat target/site/jacoco/index.html
```

À ajouter au job `junit` : la directive `coverage` applique une expression régulière au **log** du job pour en extraire le pourcentage de couverture.

# Badges : l'afficher sur le projet

Dans **Settings > Badges**, ajouter un badge :

* Lien : `https://gitlab.com/%{project_path}/-/pipelines`
* Image : `https://gitlab.com/%{project_path}/badges/%{default_branch}/coverage.svg`

Le badge affiche le pourcentage extrait par la regex lors du dernier pipeline.

[Documentation badges](https://docs.gitlab.com/ee/user/project/badges.html)
